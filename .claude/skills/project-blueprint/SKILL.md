# Project Blueprint

Every project generated or modified must look the same: same layout, same README, same frontend shell. A developer or user who knows one project must be at home in all of them.

Security rules from the `secure-app-scaffolder` skill take precedence over this skill.

**Language:** the whole project is in English (identifiers, comments, docs, README, UI strings, logs, errors) unless the user explicitly asks otherwise.

## When to Use
- Creating or restructuring a project.
- Writing or rewriting a `README.md`.
- Building or modifying any frontend page, layout or component.
- Reviewing a project for consistency.

On an existing project: apply the rules to new code; propose (do not silently perform) large reorganizations.

## 1. Project Structure

### Canonical tree
```
<project>/
├── README.md
├── Makefile                  # single entry point for every task
├── docker-compose.yml
├── .env.example              # every variable, with safe placeholders
├── .editorconfig  .gitignore  .dockerignore  .pre-commit-config.yaml
├── frontend/
│   ├── Dockerfile
│   ├── package.json  package-lock.json  tsconfig.json  vite.config.ts
│   ├── public/               # favicon, self-hosted fonts
│   ├── src/
│   │   ├── main.tsx
│   │   ├── app/              # router, providers, AppShell, error boundary
│   │   ├── features/<name>/  # one folder per business feature
│   │   │   ├── pages/  components/  api.ts  schemas.ts  types.ts
│   │   │   └── <name>.test.tsx
│   │   ├── components/ui/    # shared design-system primitives only
│   │   ├── lib/              # api-client.ts, auth.ts, i18n.ts, format.ts
│   │   ├── locales/          # en.json (other languages on request)
│   │   └── styles/           # tokens.css, global.css
│   └── e2e/                  # Playwright tests, demo fixtures, screenshots.spec.ts
├── backend/
│   ├── Dockerfile
│   ├── pyproject.toml  uv.lock
│   ├── app/
│   │   ├── main.py           # app factory, nothing else
│   │   ├── api/v1/<resource>.py   # routes: parse, authorize, call service
│   │   ├── core/             # config.py, security.py, logging.py, db.py
│   │   ├── models/           # ORM models
│   │   ├── schemas/          # Pydantic request/response models
│   │   ├── services/         # business logic
│   │   └── repositories/     # data access, user_id filtering
│   ├── migrations/
│   └── tests/                # mirrors app/
├── deploy/
│   └── nginx/nginx.conf
├── docs/
│   ├── specification.md      # functional spec, source of truth for features
│   ├── screenshots/          # README screenshots, generated by `make screenshots`
│   ├── help/                 # embedded user & admin help (Markdown)
│   └── security/             # threat-model.md
└── scripts/                  # only scripts called by the Makefile
```
Omit folders the project does not need. Never create empty placeholder folders.

### Rules
- **Allowed top-level folders:** `frontend/`, `backend/`, `deploy/`, `docs/`, `scripts/`, CI folder (`.github/` or `.gitlab-ci.yml`). Anything else must be justified.
- **Feature-first:** code for a feature lives in its feature folder. Move it to `components/ui/` or `core/` only when ≥ 2 features use it.
- **Layering (backend):** `api` → `services` → `repositories` → `models`. Routes contain no SQL and no business logic; repositories contain no HTTP concerns.
- **Forbidden names:** `utils/`, `helpers/`, `misc/`, `common/`, `stuff/`, `new/`, `old/`, `v2/`, `*_backup.*`, `*_old.*`, `test2.py`. Name files by what they do (`format.ts`, `password_policy.py`).
- **Depth:** at most 4 levels below `frontend/src/` or `backend/app/`.
- **Size:** aim for files < 300 lines and functions < 50 lines; split beyond.
- **Configuration:** environment variables only, read in one place per service (`backend/app/core/config.py` with pydantic-settings, `frontend/src/lib/config.ts`). Every variable appears in `.env.example` and in the README configuration table.

### Naming
| Element | Convention | Example |
|---|---|---|
| Python modules, functions, variables | `snake_case` | `user_service.py` |
| Python classes | `PascalCase` | `UserService` |
| React components | `PascalCase.tsx` | `UserTable.tsx` |
| Other TS files | `kebab-case.ts` | `api-client.ts` |
| Hooks | `useX.ts` | `useUsers.ts` |
| API paths | kebab-case plural nouns, versioned | `/api/v1/user-groups/{id}` |
| DB tables / columns | `snake_case`, tables plural | `user_groups.created_at` |
| Env vars | `UPPER_SNAKE`, prefixed by service | `BACKEND_DB_HOST` |

### Makefile (standard targets)
`make help` (default) · `dev` · `up` · `down` · `logs` · `test` · `lint` · `format` · `build` · `scan` · `sbom` · `clean-prod`, · `screenshots`, plus when applicable `admin-password` · `backup` · `restore-test`. `make up` only wraps `docker compose up -d`: the project never requires `make` to start. Each target has a one-line `## description` shown by `make help`. README commands use these targets.

### Code conventions
- **Tooling:** Python `ruff` (lint + format), `mypy --strict`, `pytest`. TypeScript `tsc --strict`, `eslint`, `prettier`, `vitest`. All wired in `.pre-commit-config.yaml` and `make lint`.
- **Comments:** explain *why*, never *what*. Docstrings on public functions and classes. No commented-out code, no banner comments, no TODO without a ticket reference.
- **No change-log comments:** a fix or modification never adds comments about itself (`// fixed`, `// FIX:`, `# changed from X`, `// updated`, `# now uses Y`, `// as requested`, `// new`). The code must read as if it had always been written that way; the history belongs in commit messages.
- **Minimal diffs:** a fix touches only what it requires; no unrelated reformatting or renaming.
- **Errors:** one error format for the whole API: `{"error": {"code": "USER_NOT_FOUND", "message": "...", "request_id": "..."}}`.
- **Dates:** stored and transmitted in UTC ISO 8601, displayed in the user's locale and timezone.

## 2. README Template
The README is a reference for operators and developers, not a presentation. Same sections, same order, every time.

### Writing rules
- **≤ 150 lines** (excluding collapsed `<details>` blocks).
- No emojis, badges (unless backed by real CI), marketing, roadmap, "future ideas", acknowledgements or generic "Contributing" boilerplate.
- No information about the machine that generated the project (paths, usernames, IPs, OS).
- Every command is copy-pastable and was actually run. Prefer `make` targets.
- Tables for configuration and API; bullets of one line; no paragraph longer than 3 lines.
- A section that does not apply is removed, never filled with "N/A".
- English, unless the user asked for another language.
- **Quick Start is two commands:** `git clone` + `docker compose up -d` (with `make up` and `podman compose up -d` mentioned as equivalents). It must work on the first try on a clean machine; test it before writing it.
- **Deployment targets:** Docker and rootless Podman only. No Kubernetes/Helm section.

### Screenshots
- 2 to 4 screenshots placed right after the description, before Architecture: main daily view first, then a detail/edit view, then the admin dashboard.
- Captured from the real running app by `make screenshots` (Playwright in a container against an ephemeral stack seeded with `frontend/e2e/fixtures/`, volumes removed afterwards). Never mockups, never edited images.
- 1440×900 viewport, light theme, English UI, PNG optimized to < 300 KB, stored in `docs/screenshots/` with descriptive kebab-case names (`page-view.png`), each with meaningful alt text.
- Demo data is fictitious and neutral (`example.com`, generic names, no real hostnames or IPs).
- Regenerate them when the UI changes visibly. If the app cannot run yet, tell the user instead of adding placeholders.

### Template
Copy [templates/README.md](templates/README.md) and fill it in. Keep its section names and order.

## 3. Frontend Layout & UX

### Default stack (when none exists)
React + TypeScript + Vite, React Router, TanStack Query (server state), React Hook Form + Zod (forms), an accessible headless component library (Radix UI / shadcn/ui) styled with Tailwind compiled at build time, bundled icon set (lucide). Keep the existing stack if the project already has one.

### App shell (identical on every page)
```
┌──────────────────────────────────────────────────────────────────┐
│ [Logo] App name        [ Search…  Ctrl+K ]      (?)  🔔  [User ▾] │  top bar 56px
├────────────┬─────────────────────────────────────────────────────┤
│ ▸ Dashboard│ Home / Users                                        │  breadcrumb
│ ▸ Users    │ Users                          [Filters] [+ New]    │  page header
│ ▸ Reports  │ ─────────────────────────────────────────────────── │
│            │                                                     │
│ ─ Admin ── │   content                                           │
│ ▸ Settings │                                                     │
│ ▸ Audit    │                                                     │
│ [«]        │                                                     │
├────────────┴─────────────────────────────────────────────────────┤
│ v1.4.2                                                           │  footer (version only)
└──────────────────────────────────────────────────────────────────┘
```
- **Top bar:** logo + name (link to home) left; global search center; help, notifications, user menu (profile, preferences, theme, language, sign out) right.
- **Sidebar:** max 7 top-level items with icon + label, grouped; admin entries in a separate "Admin" group visible only to admins; collapsible to icons, state remembered. Below 1024 px it becomes a drawer.
- **Page header:** breadcrumb, page title, at most one primary action (right) + secondary actions in a menu.
- **Content:** max width 1440 px for forms/detail pages, full width for tables and dashboards.
- **Help:** the `(?)` button opens the help section for the current page (`docs/help/`).

### Standard page types
| Type | Must have |
|---|---|
| **List** | Data table with search, filters, sortable columns, pagination (server-side), row click → detail, bulk actions via checkbox, column visibility, CSV export when allowed |
| **Detail** | Header with key info and status badge, tabs for sub-sections, actions menu, audit/history tab when relevant |
| **Form** | Single column, labels above fields, required marked, inline validation on blur, submit + cancel at the bottom, unsaved-changes warning |
| **Dashboard** | KPI cards on top, charts below, period selector, every number clickable to the filtered list |
| **Settings** | Left vertical tabs by section, save per section, "Reset to default" where applicable |

### Daily-use UX rules
- **Speed:** frequent actions in ≤ 2 clicks. Keyboard: `Ctrl+K` command palette/search, `/` focus search, `Esc` closes dialogs, `Enter` submits forms.
- **URL is the state:** filters, sort, page, selected tab and search are in the query string. Back button and shared links restore the exact view.
- **Remember preferences:** sidebar state, table columns, page size, density (comfortable/compact), theme and language per user.
- **Feedback:** skeletons while loading (no full-page spinners), toast on success (auto-dismiss 4 s), errors inline on the field or in a persistent banner with a retry action. Buttons show a loading state and are disabled during submission (with the idempotency key reused on retry).
- **Empty states:** short explanation + one primary action ("No users yet — [Invite a user]").
- **Destructive actions:** confirmation dialog naming the object ("Delete user *alice*?"), red button, undo toast when technically possible. No confirmation for non-destructive actions.
- **Session:** warning dialog 2 minutes before session expiry with "Stay signed in".
- **Errors:** human-readable messages, never stack traces; show the `request_id` for support.
- **Consistency:** same label for the same action everywhere (Create / Edit / Delete / Save / Cancel), same icon per concept, same position for primary actions.

### Visual system
- Design tokens as CSS variables in `styles/tokens.css`: colors (semantic: `--color-primary`, `--color-danger`, `--color-surface`…), spacing scale (4 px base: 4, 8, 12, 16, 24, 32, 48), radius, shadows, typography scale (12, 14, 16, 20, 24, 32). No hardcoded colors or pixel values in components.
- Light and dark themes, default follows the system.
- Self-hosted fonts (system font stack or bundled Inter), no external font CDN.
- Neutral, sober look: one accent color, status colors only for status.

### Accessibility & i18n
- WCAG 2.2 AA: contrast ≥ 4.5:1, visible focus ring, full keyboard navigation, labels on every input, `aria-*` on custom widgets, no information conveyed by color alone.
- All UI strings in `locales/*.json` (`en.json` by default, other languages only on request); dates, numbers and currencies formatted with `Intl`.

## Checklist
- [ ] Tree matches the canonical layout; no forbidden folder names; no empty folders.
- [ ] `make help` lists all standard targets.
- [ ] Every env variable is in `.env.example` and the README table.
- [ ] README follows the template, ≤ 150 lines, no fluff, with real screenshots.
- [ ] `docker compose up -d` works on a fresh clone without `.env` or `make`.
- [ ] Every page uses the AppShell and one of the standard page types.
- [ ] Lists keep their state in the URL.
- [ ] Loading, empty and error states exist for every data view.
- [ ] Light/dark themes, keyboard navigation and i18n work.
- [ ] Everything is in English (unless requested otherwise).
- [ ] No change-log or AI-generated comments describing modifications.
